Project rules instead of check scripts

Coding agents write a new scripts/check-*.mjs each time a project needs a check that no linter provides. vibator gives those checks one home: a rule is one file in.vibator/, and npx vibator runs them all.

npm install --save-dev vibator
npx vibator init
npx vibator
pnpm add --save-dev vibator
pnpm exec vibator init
pnpm exec vibator
bun add --dev vibator
bunx --bun vibator init
bunx --bun vibator

Requires Node 24 or later, or Bun 1.4.2 or later. init writes a starter rule in .vibator/. With Bun, --bun runs vibator on Bun instead of Node.

From custom scripts to a rule set

Every check script becomes a rule. Each step below builds on the one before it.

1

Replace check scripts with rules

A check script writes its own file walk, parsing, output, and exit code. A rule is the check alone, one file in .vibator/. vibator does the rest.

From script to rule

Read themreadFileSync, regex loopstext.search, ts.parse

2

Read the whole project through one API

A rule reads files, JSON, TypeScript syntax trees, package.json, git, and the shell through vibator. It never imports fs.

It sees every file at once, so it can compare files with each other.

Namespace reference
  • vibator.projectFiles and folders
  • vibator.textLines and search
  • vibator.jsonValues and key paths
  • vibator.tsSyntax trees and types
  • vibator.packagepackage.json manifests
  • vibator.moduleImport resolution
  • vibator.gitStaged and changed files
  • vibator.shellRun a command
  • vibator.globMatch paths
  • vibator.ignoreIgnore markers
3

Findings that say what to do

Each finding keeps three fields apart: message says what is wrong,expected states the standard, and fix gives the next action.

A person or an agent acts on a finding without reading the rule.

Rule definition
4

One report for every rule

Every rule reports in the same format, with the file, line, column, and the code around it.

--reporter json feeds your own tools. --reporter sarif feeds code scanning.

Reporters
5

Fix what a rule can fix

A rule can implement fix. With --write, vibator runs the check, the fix, and the check again.

The report shows only what the fix left.

Rule definition
  1. checkFinds the problems
  2. fixChanges the files
  3. checkReports what is left
6

Run it where the work happens

--staged, --changed, and --since scope a run to the files git reports, for a pre-commit hook or a pull request job.

.vibator.json sets a severity per rule. An error fails the run, a warning reports and passes.

7

Test rules like code

runRule from vibator/testing runs one rule against content you write in the test. It works in any test runner.

Test a rule
8

Let agents write and fix rules

vibator ships three skills for Claude Code and compatible agents.npx vibator skills --install copies them into the project.

An agent then writes a rule instead of a script and fixes what the rules report.

Agent skills
  • writing-vibator-rulesWrites a rule in .vibator/ instead of a check script.
  • fixing-vibator-findingsActs on each finding's message, expected, and fix.
  • configuring-vibatorSets severities, options, and plugins in .vibator.json.
9

Extend the namespace with plugins

A plugin is a package that adds its own namespace to vibator withdefineNamespace, such as vibator.i18n. Every rule in a project that loads it reads the namespace like the built-in ones, with its types.

A plugin can also ship rules that use its namespace.

Plugins and shared configuration
10

Share one config across repositories

A base config sets the plugins and the severities once. Each repository extends it and overrides only what differs.

Plugins add up, and rules merge by id, so the project's severity wins.
